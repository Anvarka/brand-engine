Twenty minutes was the latency budget that let me remove an entire server.

The goal was a LinkedIn post every two days with roughly 30 seconds of manual work. Approval happens in Telegram: I read a draft and tap an inline button.

The tempting path was to publish directly from that tap. I did not build it that way.

LinkedIn does not provide scheduled publishing through its API. The publishing slot therefore had to be controlled by my system regardless of when I approved a draft. I split approval and publishing into separate scheduled jobs: one polls the approval state, another publishes at the planned slot.

That means an approval can wait up to 20 minutes to be observed. For a post scheduled days ahead, that delay has no user-facing cost. A direct approval flow would have required a webhook server merely to achieve immediacy that the scheduler could not use.

The rest runs in GitHub Actions. A critic scores each draft against a rubric before I see it. The pipeline has six scheduled workflows, zero servers, and model spend of about $0.03–$0.05 per post.

My rule: if you already own the schedule, separate approval time from execution time.

<!-- variant_b -->
The obvious “Approve” button was the wrong place to publish a post.

The first design I considered treated approval as an event: tap a Telegram button, trigger a LinkedIn publish call. It would have felt immediate, but it also would have made this small pipeline depend on a webhook server.

The actual constraint was not approval latency. LinkedIn’s API has no scheduled publishing. I still needed to own the publishing slot, which meant I needed a scheduler regardless.

So I changed the boundary. Approval records a decision; publishing is a separate scheduled job. A polling workflow notices that decision, with up to 20 minutes of lag, and another workflow releases the post at its slot.

For a cadence of one post every two days, that lag is operationally irrelevant. The direct path added infrastructure without improving when the post could go live.

The system now runs entirely on GitHub Actions. Telegram is only the approval surface, and a critic scores drafts against a rubric before they are shown. Six scheduled workflows do the work. There are zero servers, and model spend is about $0.03–$0.05 per post.

I would only pay for event-driven approval when approval itself changes execution time.

Лимит задержки в двадцать минут позволил мне убрать целый сервер.

Целью был пост в LinkedIn раз в два дня примерно с 30 секундами ручной работы. Одобрение происходит в Telegram: я читаю черновик и нажимаю inline-кнопку.

Самым очевидным решением было бы публиковать пост прямо после этого нажатия. Но я сделал не так.

LinkedIn не предоставляет через API возможность планировать публикацию. Поэтому момент публикации в любом случае должна была контролировать моя система — независимо от того, когда я одобрил черновик. Я разделил одобрение и публикацию на две отдельные scheduled jobs: одна проверяет состояние одобрения, другая публикует пост в запланированный момент.

Это значит, что одобрение может ожидать до 20 минут, прежде чем система его заметит. Для поста, запланированного на несколько дней вперёд, такая задержка не имеет пользовательской цены. Прямой flow одобрения потребовал бы webhook-сервер лишь для того, чтобы обеспечить мгновенность, которой scheduler всё равно не мог воспользоваться.

Остальное работает в GitHub Actions. Перед тем как я вижу черновик, critic оценивает его по rubric. В pipeline шесть scheduled workflows, ноль серверов, а расходы на модели составляют примерно $0,03–$0,05 на пост.

Моё правило: если расписание уже у вас под контролем, разделяйте время одобрения и время выполнения.

Очевидная кнопка «Approve» оказалась не тем местом, где стоило публиковать пост.

В первом варианте, который я рассматривал, approval был событием: нажатие кнопки в Telegram запускало вызов LinkedIn API для публикации. Это ощущалось бы моментально, но при этом заставило бы небольшой pipeline зависеть от webhook-сервера.

Фактическое ограничение было не в задержке approval. У LinkedIn API нет отложенной публикации. Мне всё равно нужно было самому управлять моментом публикации, а значит, scheduler требовался в любом случае.

Поэтому я изменил границу ответственности. Approval фиксирует решение, а публикация выполняется отдельной scheduled job. Polling workflow замечает это решение с задержкой до 20 минут, а другой workflow выпускает пост в назначенный slot.

При cadence в один пост каждые два дня такая задержка операционно несущественна. Прямой путь добавлял инфраструктуру, но не позволял опубликовать пост раньше.

Теперь система целиком работает на GitHub Actions. Telegram — это только интерфейс approval, а critic оценивает черновики по rubric до того, как они показываются. Всю работу выполняют шесть scheduled workflows. Серверов нет, а расходы на модели составляют примерно $0.03–$0.05 на пост.

Я бы платил за event-driven approval только в том случае, если сам approval меняет время выполнения.
